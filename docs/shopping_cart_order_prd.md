# 购物车与下单功能产品需求文档 (PRD)

## 1. 业务目标与背景
本项目旨在实现基于多店铺体系的购物车管理与订单结算功能。重点优化未登录用户的加购体验，实现未登录到登录状态的购物车数据无缝合并。同时，支持按单店铺维度进行独立的订单结算，并完善用户的收货地址管理。

---

## 2. 功能模块一：多店铺购物车与登录合并流程

### 2.1 购物车基础交互
- **跨店铺加购**：在店铺详情页，用户可以添加该店铺的多个商品到购物车。购物车系统需要支持存储不同店铺的商品。
- **游客加购**：用户无需强制登录即可将商品加入购物车。

### 2.2 底部结算条与“下单”操作
- **按钮状态联动**：
  - **置灰状态**：当用户在当前浏览的店铺中未选择任何商品时，“下单”按钮显示为灰色且不可点击。
  - **可点击状态**：当用户在当前浏览的店铺中勾选/添加了商品时，“下单”按钮高亮并变为可点击状态。
- **下单跳转逻辑**：
  - **已登录用户**：点击“下单”后，直接跳转至【确认订单页】。
  - **未登录用户**：点击“下单”后，携带当前回跳地址（即确认订单页的路由），跳转至 `badger-web` 系统的登录页。用户登录成功后，自动跳转至【确认订单页】。

### 2.3 购物车数据流转与合并（核心机制）
- **未登录数据存储方案**：
  - 客户端：将游客的购物车数据存储在浏览器的本地存储中（LocalStorage / 离线数据）。
  - 服务端：基于设备指纹或临时 Session ID，将对应的购物车数据同步缓存在 Redis 中，防止本地数据丢失。
- **登录合并机制**：
  - **触发时机**：用户在任何页面触发并完成登录操作后。
  - **合并规则**：系统需自动读取游客态的购物车数据（本地缓存或 Redis），并与该用户账号下原有的线上购物车数据进行合并。合并完成后，清空游客态对应的临时数据。

---

## 3. 功能模块二：单店结算与地址管理

### 3.1 确认订单页（下单页）
- **数据隔离展示**：用户进入确认订单页后，页面**仅显示触发下单的那个特定店铺**的购物车商品明细，而非用户名下所有店铺的购物车商品。
- **订单金额计算**：根据当前展示的单店商品清单，自动计算商品总价、优惠及应付金额。

### 3.2 收货地址管理 (CRUD)
用户在确认订单时，需要能够管理并选择配送地址。需实现以下闭环功能：
- **查询地址列表 (Retrieve)**：展示当前用户保存的所有收货地址，并支持设置/显示默认地址。
- **新增地址 (Create)**：支持填写联系人、电话、所在地区及详细地址进行保存。
- **修改地址 (Update)**：支持对已存在的地址信息进行编辑更新。
- **删除地址 (Delete)**：支持移除不再使用的收货地址。

### 3.3 提交订单操作
- 用户确认单店铺的商品清单，并选择好配送地址后，点击“提交订单”完成最终的下单流程。生成对应的订单记录，并流转至后续支付环节（预留）。

---

## 4. 后续技术拆解建议
1. **数据库设计**：购物车表（需兼容用户ID和临时ID）、收货地址表、订单表。
2. **Redis 数据结构**：规划游客购物车在 Redis 中的 Hash 结构设计及过期策略。
3. **SSO 拦截与鉴权**：前后端配合处理跳转 `badger-web` 的鉴权与回调逻辑。
4. **前端状态管理**：使用 Pinia/Vuex 维护全局的购物车数量及合并后的状态同步。
